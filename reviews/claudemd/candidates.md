- [rbac/security] **Mutation gating requires TWO checks** — `requirePermission(<RESOURCE>, <ACTION>, eventId)` ONLY confirms the caller's role grants the action at the (resource, scope) the eventId resolves to. It does NOT confirm the supplied entityId belongs to that eventId. Without a second check, a caller with `ASSIGNED:WRITE` on event A can pass entityId from event B and the resource gate still grants access — they then mutate event B's data. PR3 enforces ownership via three patterns, choose the one that fits: (a) **top-level entities** (Function, AVOrder, …): add `eventId` to the Prisma `where` clause directly — `where: { id, eventId }` (Prisma 6 extended-where-unique supports this). (b) **sub-entities one+ levels deep**: add a relation filter — `where: { id, function: { eventId } }` or `where: { id, inputGroup: { audioSection: { avOrder: { eventId } } } }`. (c) **create-style mutations** where Prisma's where can't carry the constraint: pre-check via a colocated helper — `async function assertFunctionInEvent(functionId, eventId) { const found = await prisma.function.findUnique({ where: { id: functionId, eventId }, select: { id: true } }); if (!found) notFound(); }`. **Bulk mutations** (`updateMany`/`deleteMany`) always include the eventId filter (`where: { id: { in: ids }, eventId }`) — that's the reference pattern, already used by every `bulkUpdate*`. The seeded default User role grants every event resource at every scope, so the bug is invisible under defaults — but any custom role using `ASSIGNED` as a security boundary depends on this enforcement.

- [inventory] `InventoryItem.equipmentId` is REQUIRED, not optional — inventory is catalogued gear, so the Equipment link is identity and `name` is only a qualifier ("blue", "spare"). This is what makes stock answerable across locations ("how many easels, and where?"), which free text can't do. Consequence chain worth remembering: required link forces `onDelete: Restrict` on the Equipment FK (SetNull is unavailable once the column is non-null), and forces post-event "Return to…" to skip supply lines that have only a free-text description — it names them so they can be catalogued and retried.
- [permissions] EQUIPMENT is admin-only while STORAGE_LOCATIONS is User-WRITE, so any feature that makes one depend on the other splits by role. Requiring an Equipment link on inventory means a packer can file catalogued gear but cannot extend the catalog; the inline "＋ New equipment" affordance is gated on EQUIPMENT WRITE and simply absent for them. Decided deliberately over granting the User role EQUIPMENT WRITE. General lesson: when two resources sit on opposite sides of the admin boundary, check which role actually performs the task before coupling them — testing as admin hides this entirely.
- [mcp] A required FK on a write tool needs a companion read tool to discover ids, or the write tool is unusable over MCP. `create_inventory_item` requires an `equipmentId` and no equipment catalog tool existed, so `list_equipment_catalog` shipped alongside it. Check this whenever an MCP write takes an id the caller can't already obtain from another tool's output.
- [mcp/permissions] An MCP tool should gate at the permission the *app* enforces for the same read, not the one that merely shares the resource's name. `list_equipment_catalog` gates on STORAGE_LOCATIONS VIEW rather than EQUIPMENT VIEW, because EQUIPMENT is admin-only while `getEquipment()` is deliberately auth-only so every order form can render a picker — gating on EQUIPMENT would make MCP stricter than the UI for the same user and block a packer from filing inventory they can file on screen.
- [auth] CLAUDE.md cites `requireAdmin()` in four places (Architecture invariants, Server Actions, Security and validation, Further reading) but it no longer exists anywhere in `src/`. Admin segments now gate via `requirePermission(RESOURCE, ACTION)` (`src/app/settings/layout.tsx`) or `hasGlobalView` + `redirect("/")` (`src/app/users/layout.tsx`). Update the rubric to describe the RBAC-era pattern.
- [events] `eventScopeWhere(userId)` in `src/app/events/core.ts` is now the single definition of "which events may this user see" (role EVENTS:UNASSIGNED above NONE → all; otherwise `staff: { some: { userId } }`). Any new list that returns events — page, action, or MCP tool — must AND it in, or it becomes a way to enumerate events the caller can't access. Was duplicated in `getEvents` + MCP `list_events` and got missed twice when adding the series page.
