- [rbac/security] **Mutation gating requires TWO checks** — `requirePermission(<RESOURCE>, <ACTION>, eventId)` ONLY confirms the caller's role grants the action at the (resource, scope) the eventId resolves to. It does NOT confirm the supplied entityId belongs to that eventId. Without a second check, a caller with `ASSIGNED:WRITE` on event A can pass entityId from event B and the resource gate still grants access — they then mutate event B's data. PR3 enforces ownership via three patterns, choose the one that fits: (a) **top-level entities** (Function, AVOrder, …): add `eventId` to the Prisma `where` clause directly — `where: { id, eventId }` (Prisma 6 extended-where-unique supports this). (b) **sub-entities one+ levels deep**: add a relation filter — `where: { id, function: { eventId } }` or `where: { id, inputGroup: { audioSection: { avOrder: { eventId } } } }`. (c) **create-style mutations** where Prisma's where can't carry the constraint: pre-check via a colocated helper — `async function assertFunctionInEvent(functionId, eventId) { const found = await prisma.function.findUnique({ where: { id: functionId, eventId }, select: { id: true } }); if (!found) notFound(); }`. **Bulk mutations** (`updateMany`/`deleteMany`) always include the eventId filter (`where: { id: { in: ids }, eventId }`) — that's the reference pattern, already used by every `bulkUpdate*`. The seeded default User role grants every event resource at every scope, so the bug is invisible under defaults — but any custom role using `ASSIGNED` as a security boundary depends on this enforcement.
